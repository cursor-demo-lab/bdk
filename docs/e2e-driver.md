# e2e driver: how `scripts/e2e-drive.mjs` scores a run

Moved from the factory README. `scripts/e2e-lib.test.mjs` holds this page to the rules the driver scores by.

Whole flow, asserted: `node scripts/e2e-drive.mjs` (or `--ticket TLSSN-3`; `--help` for steps) replays each Jira hop, drives Approved, opens the two marsbank test PRs, and prints one row per step, marked `pass`, `pass (prior run)`, `fail`, `blocked`, `unverified`, or `skipped` (it exits 1 on any `fail`); for the GitHub steps, create a fine-grained token on `cursor-demo-lab/marsbank` (Contents read, Pull requests write, Issues write, Actions read) and put it in `.env.local` as `FACTORY_E2E_GITHUB_TOKEN`. Without that token the driver runs `--github=cloud-agent`: each GitHub write is one Cursor cloud agent launched with your `agent-sdk login` key, and the driver only reads GitHub (with `gh auth token`) to verify the result.

How the driver reads Jira:

- Each new ticket gets a stamped summary (`Factory e2e MMDD-HHMMSS: ...`). Triage calls an exact title match a duplicate, and the planner does not plan duplicates.
- Every comment and status move is attributed by Jira `accountId`. The driver's REST token (`<OPERATOR_EMAIL>`) and the Factory Atlassian consent (`<OPERATOR_EMAIL>`) both display as "the operator", so the display name cannot tell them apart. The driver reads its own id from `GET /myself`; if that call fails three times, a poll interval apart, every Jira step is `blocked` before anything is written. A move the driver made never counts as an agent pass, even if its id is in the pin: its stand-in moves when an upstream step is skipped, a concurrent run, or a person using the same token.
- Pin the agent with `FACTORY_E2E_AGENT_JIRA_ACCOUNTS` in `.env.local` (on this site the consent is `712020:95b89517-2f6d-49a8-ab77-0d2e88c97ae3`). Pinned, only those ids are "the agent account" and any other author leaves the hop `unverified`. Unpinned, any author but the driver counts and the reason names it "a non-driver account (id)", since the driver cannot prove whose it is.
- Each row prints `evidence:` lines. Jira rows: the comment id, author and excerpt, the changelog id, move and author, the replayed changelog, and the route's HTTP status, all with UTC timestamps. A Jira `pass` needs both a comment line and a changelog line by a non-driver account. GitHub rows: `prs` needs the PR number and author, `review` the review id, author and reviewed commit, `red-check` a failed CI run id, a commit pushed by a fixer login with the workflow run that names the pusher, and a successful CI run id, and `drive` the fixer's first comment id with its author, or its first commit pushed by the fixer with the workflow run that names the pusher. A commit line prints the git author login ("authored as", never scored) apart from the pusher ("pushed by L (actor of workflow run N)", or "pusher unknown"). A pass row without them is `unverified`, never `pass`.
- The GitHub rows gate on who acted, the way the Jira rows do. `drive` and `red-check` count only comments and pushes by the logins in `FACTORY_E2E_FIXER_LOGINS`, and the green tip of `red-check` must be a fixer push. Unset, those two rows are `unverified` at best and name the actor as "a non-driver account (login)": the fixer's GitHub identity is not confirmed yet ([docs/next-steps.md](docs/next-steps.md), step 7), so there is no default. `review` passes only on a `## Security review` by a login in `FACTORY_E2E_REVIEWER_LOGINS` (default `cursor[bot]`). The driver's own GitHub login never counts, even when it is listed (except in `drive` in cloud-agent mode, below).
- Who pushed a commit is the `actor` of the `push` or `pull_request` workflow run GitHub started for it (the earliest such run by `created_at`; they must all name one login, compared case-insensitively). A re-run keeps the run's `actor` and `created_at`, so the pusher is never whoever re-ran it (`triggering_actor`) or when (`run_started_at`). A run whose `head_sha` is another commit never counts. The commit's author login is never read as the pusher: anyone who can push can set it, and a fixer-authored commit pushed by someone else is not the fixer's push. A commit with no such run, or whose runs name two logins, has no pusher, so it never counts: if it is the green tip, `red-check` is `unverified`. Such a commit is one pushed together with newer ones (GitHub starts runs for the newest commit of a push only), or one on a branch with no workflow for it.
- A workflow run counts, for CI state and for the pusher, only when it is bound to the PR being read: its `head_sha` is the commit, its `head_branch` is the fixture branch, its `head_repository` is `cursor-demo-lab/marsbank`, and every entry of its `pull_requests` is this PR's number on that repository. `GET /actions/runs?head_sha=` is repository-wide, so the same commit on another branch, a fork, or another PR returns runs too. A run with an empty `pull_requests`, or one that also lists another PR, never counts. A commit whose runs are all unbound has CI `none` and no pusher.
- Reopens and the opening: a `pull_request` run started by reopening the PR names whoever reopened it, an `opened` run names whoever opened it, and a commit pushed while no PR was open may have no other run, so that login would read as the pusher. The runs API does not say which `pull_request` action started a run, so the driver reads the PR's `reopened` issue events and its opening (`user.login` and `created_at` on `GET /pulls/{n}`; `decidePr` reuses the one open PR on the fixture branch, whoever opened it). It pins each event to the commit of its own run: the earliest `pull_request` run by the event's login from 5 seconds before the event to 600 seconds after it, both ends included, among the runs of every commit read. A pinned event drops that login's `pull_request` runs on its commit from 5 seconds before the event on, and none on another commit, so a later push by the same login counts. An event with no run in the window is not pinned and drops that login's `pull_request` runs inside the window only, so a run 601 seconds after the event reads as a push. A (re)open event or run whose time does not parse drops every `pull_request` run by that login, so a missing time never reads as a push. A commit whose only run was dropped has no pusher, and a green tip is `unverified`. Known limits: an unpinned event misses a run that GitHub Actions starts more than 600 seconds late (marsbank's opening runs land 3 to 4 seconds after the PR opens), and the pin takes the earliest run, so if Actions created a later push's run before the event's own, that push reads `unverified` and the event's own commit keeps the login's run. On the fixtures: a PR the driver opens in token mode is authored by the driver's own login, which never counts. In `--github=cloud-agent` mode, a PR the agent opens as the fixer's login (`cursor[bot]`, as `autoCreatePR` does) pins to the commit it was opened on, the red commit or the review commit, and a fixer push on a new commit counts at once. Only when that opening run was not read does a fixer push within 600 seconds of the opening read `unverified`.
- Cloud-agent commits on marsbank are signed (`verification.verified: true`, committer `cursoragent`), but the driver does not score that. Every Cursor cloud agent on the account (the worker, the fixer, a one-off run) commits as `cursoragent`, so it cannot tell the fixer from another agent, and a signature says who made the commit, not who pushed it.
- `review` passes only on the reviewer's own shape: a PR review in state `COMMENTED`, by a pinned login, whose body opens with `## Security review`, a blank line, then `**Verdict:** CLEAN` or `**Verdict:** FINDINGS` (what `security-reviewer`'s `post_findings` tool writes), on the PR head commit. An issue comment, another state, another body, or a review of an older commit is `unverified`.
- At the timeout a GitHub row whose every candidate was by a person (GitHub user type `User`), the driver's own login, or a login outside the pin is `fail (wrong actor)`, and the run exits 1. When any candidate has no login or no pusher, was dismissed, or nothing is pinned, the row is `unverified`.
- Caveat, a shared login: cloud agents comment as `cursor[bot]`, the same login as the default reviewer pin. If the fixer's pushes arrive as `cursor[bot]` too and you pin it in `FACTORY_E2E_FIXER_LOGINS`, any `cursor[bot]` comment or push after `factory: drive` starts `drive` (Bugbot and `## Security review` items excepted) and any `cursor[bot]` push can be the `red-check` fix. `pr-autofixer` posts no comment of its own (its cloud agent only pushes), so there is no fixer marker the driver could require instead. `review` is narrowed by its body shape; `drive` and `red-check` are not.
- Caveat, cloud-agent mode: the `factory: drive` comment is posted by a cloud agent, so `drive` runs with `driverLogin: undefined` (`scripts/e2e-drive.mjs`, the `evaluateDrive` call) and excludes only that comment itself. The driver's own GitHub login is not excluded from `drive` in that mode; `review` and `red-check` still exclude it.
- Reviews, issue comments, PR commits and PR issue events are read page by page. `review` and `red-check` take the PR head from the pull request (`head.sha`), not from the order of the commits list; if the head is not among the commits `red-check` read, it waits, then fails at the timeout. A pull request with no `head.sha` makes both rows wait, then read `unverified`; the list order never stands in for the head. Both rows read the pull request again after the evidence (the reviews, or the commits and runs): when it is no longer open or its head moved, the row waits for a poll where both reads agree, and is `unverified` if none does by the timeout. GitHub's PR commits list stops at 250, so a PR with 250 or more commits fails `red-check` and `drive` at the timeout ("could not read state") rather than guessing. `red-check` and `drive` read workflow runs for the newest 10 commits only: a red commit older than those makes `red-check` `unverified`. Reads per poll: `review` reads the PR, its reviews, its issue comments, then the PR again; `red-check` reads the PR, its commits, its issue events, and one workflow runs call (up to 50 runs) for each of the newest 10 commits, then the PR again; `drive` reads reviews, issue comments, commits, the PR, issue events, and the same 10 runs calls. Each list is 100 items a page, so at the 250 cap a `red-check` poll is at most 2 + 3 + the event pages + 10 calls. Until some commit is red, `red-check` waits while any commit it read has CI queued, running, or not started, because that commit can still go red; only once all of them are red or green, or at the timeout, is "no red commit" `unverified`, `blocked`, or `fail`.
- In token mode `prs` reuses a fixture PR only when it is the one open PR on that branch and its base is `main`. Two or more open PRs on the branch are a `fail`, one into another base is `unverified`, and the steps that read that PR are `blocked`. A reused PR whose title is not the fixture's title (for the red PR, lacks its prefix) is retitled, so it is `pass`, not `pass (prior run)`. `--github=cloud-agent` mode checks the same things after the agent runs (`verifyAgentPr`).
- A hop the ticket had already finished before this run (a rerun with `--ticket`) is `pass (prior run)`: the driver scores it on the ticket as the run found it (the comments and moves written before the run started) and sends nothing to its route. GitHub rows do the same: reused PRs the run did not retitle ("already open before this run, nothing written"), and a review, green fixer push, or drive start that predates the run ("already done before this run, nothing written") are `pass (prior run)`, never `pass`. The table counts them apart from `pass`. When any pass row only re-read state from before the run (a prior-run hop, a reused ticket the run did not reset, reused PRs the run did not retitle, or a review, green fixer push, or drive start that predates the run), the summary adds a note naming those rows and counting the pass rows that came from this run's sends or writes and the route POSTs sent. The table starts with the run's start time.
- `docs/jira-automation.md` is the live ingress: five TLSSN project Automation rules with `X-Factory-Webhook-Secret`. `docs/jira-webhooks.md` is the optional HMAC system-webhook path. Replay mode still signs every route with the root `.env.local` `JIRA_WEBHOOK_SECRET`. A replay-mode pass does not prove a Jira-originated request triggered the agent, and a route's `202` is only an ingress receipt: hosted v2 answers 202 before the handler runs.
- The `Implementing:` URL is read from the text itself or from an `inlineCard`, `blockCard` or `embedCard` (`attrs.url` or `attrs.data.url`), on the same line or the next. Link-marked text reads as its text, not its `href`, because Jira link-marks issue keys and `Plan: <key>` must still match.
- `announce` replays Planned and `progress` replays In Progress to factory-desk. Both can be `unverified` at best, because the desk writes only to Slack and the driver has no Slack access.
- A hop that fails for a missing or stuck artifact says `Atlassian connector: authorised` only when the agent account wrote a sentinel comment during the run. Otherwise it says `unknown`. The driver cannot see the connector, so it never reports it as "not authorised".
