APJ GTM · Software factory

End to end on Slack, Jira, and GitHub

A person opens a request with @Factory in one Slack thread, reacts ✅ twice (once to file, once on the plan), then reviews and merges on GitHub. Plain replies in the thread need no mention. Six hosted agents run, one per stage, and none calls another: each writes its artifact to the Jira ticket and moves it, and the next wakes on that status. The thread reads: the filing prompt with Jev's triage, ✅, the Filed post, Triaged, the plan post, ✅, exactly one In Progress post, the marsbank pull request, review updates (🐛 🔒 🏗️ 📡 🔧, in that order), and In Review. The swimlane with every artifact is e2e.html.

1 · Amplitude stages: Intake, Ticket

A thread files the ticket, and triage classifies it

In #mars-eng-intake a person opens a request with @Factory. Before anything is filed the desk asks Jev to triage it (its grok-4.6-fast turn triages when Jev is unsure) and posts one filing prompt. The requester's ✅ on that prompt files the issue in TLSSN, writes the Triage: comment, moves it to Triaged, and posts the Filed post. Triage-jira skips a desk-filed ticket; it triages tickets filed in Jira directly.

A ticket filed in Jira directly takes the same path. The desk then opens one root post for it in #mars-eng-intake, and it can be approved only on the board.

The status change is the handoff. Triage does not call the planner.

2 · Amplitude stage: Plan

The planner writes the plan, and the desk posts it

The Triaged rule wakes factory-planner. It reads the ticket and the sandbox, writes one Plan: comment that ends in a Brief:, and moves the ticket to Planned. The Planned rule wakes the desk, which posts the plan into the thread.

3 · Amplitude stage: Open the pull request

✅ on the plan is the launch

The filer reacts ✅ on the plan post (or replies a plain approve). Host code moves Planned to Approved and records the Slack approval, so the Approved webhook stays quiet. The Approved rule wakes factory-worker, which launches one cloud agent from the brief, comments Implementing: with its URL, and moves the ticket to In Progress. The desk posts exactly one In Progress post with the URL.

There are no Slack cards or buttons: every gate is a ✅ / ❌ reaction on the filing prompt or plan post (reaction_added, 0.2.11), or the same decision as a plain reply. A later approval that finds the worker's launched claim does not launch again. Two approvals that race usually launch once: the claim re-reads its own owner after a 2 s settle, but with no compare-and-set a put slower than that can still let both launch, and whether the idempotency key then prevents a second agent is unchecked.

The pull request opening moves the ticket. No Jira rule and no GitHub for Jira transition does it.

4 · Amplitude stages: Bugbot, Security pass

The pull request opens: In Review, and two reviews

5 · Amplitude stages: Failed build, Autopilot

A red check drives the fixer

A failed check_suite or workflow_run on a pull request whose branch starts with a ticket key (or whose title does, when cursor[bot] opened it) starts pr-autofixer with no request. Any other pull request needs a person to type factory: drive on it in GitHub. Asked in Slack to fix a pull request, the desk replies with that instruction and writes nothing to GitHub.

Each push runs CI and Bugbot again and wakes the security reviewer on synchronize. GitHub's own Slack app can post failures to #factory-escalations for people to read; nothing in the factory subscribes to it.

Nothing in the factory merges. A person does, and that merge is what closes the ticket.

6 · Amplitude stages: Risk gate, Merge

A person merges, and the ticket is Done

A person checks CI, Bugbot, and one review, then presses Merge. factory-worker hears the merge and moves the ticket from In Review to Done without writing a second Pull request: comment. A merge by a bot or app, or by GitHub auto-merge, never moves it. The desk posts KEY is Done: owner/repo#N was merged.

Jira Automation rules

Five rules in the TLSSN project carry the status bus. Every rule sends a web request with method POST, header Content-Type: application/json, and the hidden header X-Factory-Webhook-Secret (its value is the slug's secret; never paste it into docs), with "Wait for response" unticked. Full setup: jira-automation.md.

RuleTriggerURL (channel path)Body
Jira Automation factory-deskWork item transitioned to In Progress, Planned, Approved, In Review, Done or Triaged.../agents/<desk agent id>/engine/v1/channels/jira/Status body
Jira Automation factory-plannerTransitioned to Triaged.../agents/<planner agent id>/engine/v1/channels/webhook/Status body
Jira Automation factory-workerTransitioned to Approved.../agents/<worker agent id>/engine/v1/channels/jira/Status body
Jira Automation factory-desk-commentsComment added (all comments)desk .../channels/jira/Comment body
Jira Automation factory-triage-jiraWork item created.../agents/<triage agent id>/engine/v1/channels/webhook/Triage body
  • Every free-text smart value uses .jsonEncode Summary, description, reporter name, and comment body are encoded. An unescaped quote in a title made invalid JSON that the host dropped silently while Jira still logged "Successfully published web request". That broke planning for TLSSN-40/41.

Automations as code (cursor-agent + YAML)

The live factory runs as the six hosted Agent SDK (@cursor/july 0.2.18) deployments: the Jira rules above POST to the hosts' engine channel URLs, and GitHub events arrive through --cursor-events-repo. The same event wiring is also written as Cursor Automations config-as-code, one file per role at the repo root in .cursor/automations/factory-*.yaml, deployable with cursor-agent automations deploy. Each spec runs claude-opus-5-5 at low effort and its prompt points at the host's AGENTS.md in the checkout. There is no Jira trigger kind, so the Jira rules map to webhook: {}. Two out-of-the-box templates sit beside them, also enabled: false: find-vulnerabilities.yaml ("Find vulnerabilities" on marsbank PRs) and find-bugs.yaml ("Find critical bugs", not Bugbot). Bugbot, the managed Security Reviewer, and change monitor have no YAML form; turn them on in the dashboard (Bugbot rules live in .cursor/BUGBOT.md). Full guide: cursor-agent-automations.md.

  • The specs ship enabled: false Deploying them next to the live hosts cannot double-handle an event. Enable one only when it replaces (or shadows, pointed elsewhere) the matching host. A disabled deploy still creates the record, so validate, get --yaml, and test work.
  • The automations verbs are gated They need the automations_config_as_code gate on the account. If cursor-agent automations --help prints only the main help, the gate is off. agent is the same binary.

What the picture leaves out

  • Jira is the bus. Five TLSSN project Automation rules carry every Jira hop (below), each with X-Factory-Webhook-Secret set to the slug's secret. GitHub hops reach the worker, fixer, and reviewer through githubChannel({ cursorAccount }), deployed with --cursor-events-repo cursor-demo-lab/marsbank. No agent calls another.
  • The desk's rule lists six statuses. Triaged, Planned, Approved, In Progress, In Review, and Done, with Allow rule trigger ticked. Without Triaged the thread is silent from filing to the plan; without In Review and Done it goes quiet after "KEY is In Progress". No rule transitions a ticket from a pull request: disable any GitHub for Jira "created" or "merged" transition rule.
  • Reaction gates, no buttons. Hosted v2 inbound is message, app_mention, and reaction_added (0.2.11); the Slack app needs reactions:read and the reaction_added event. The requester's ✅ / ❌ on the filing prompt and the filer's ✅ / ❌ on the plan post are the gates; a plain reply (approve file, approve) does the same. New requests start with @Factory; replies in a factory thread need no mention. Dragging the card on the board does the same launch, under Jira permissions, and that path still posts the Approved line.
  • Human merge only. No agent merges, enables auto-merge, or force-pushes. The worker moves a ticket to Done only when a person merged its implement pull request, and only for a ticket it launched. Merge does not write a second Pull request: comment.
  • Code, then live. This walk follows the factory code on main. The full step list is e2e.html; what was seen live is in verification.md.
