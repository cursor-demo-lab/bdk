One ticket, end to end

Alice stays in Slack from filing to merge. She opens a request with @Factory in #mars-eng-intake. The desk asks Jev to triage it before anything is filed, posts a filing prompt, and waits for her ✅ (file it) or ❌ (drop it) reaction on that prompt. Six hosted agents run, one per stage. Hosted, none of them calls another. Each stage writes its artifact to the Jira ticket, then moves the ticket. The next agent wakes on the status it moved to. Statuses are To Do → Triaged → Planned → Approved → In Progress → In Review → Done.

The thread then reads, in order: the Filed post, Triaged, the plan post, her ✅ on the plan, exactly one In Progress post with the agent URL, the marsbank pull request (cursor-demo-lab/marsbank), review updates whose gate lines always run 🐛 Bugbot, 🔒 security review, 🏗️ CI, 📡 change review, 🔧 autofix, and In Review. A ✅ on the plan moves the ticket Planned → Approved through host code (approvePlanned) and records approved-in-slack/<KEY>, so the Approved webhook posts nothing and the next beat is In Progress. A ❌ on the plan leaves it Planned with a Denied in Slack comment. A card dragged to Approved on the board still gets an Approved line, because it has no Slack-approval record.

There are no Slack cards or buttons. The gates are ✅ / ❌ reactions: July 0.2.11 delivers reaction_added on hosted v2, so the Slack app needs the reactions:read scope and the reaction_added event. Only a reaction on a post the desk recorded (the filing prompt, the plan post) counts, and only from the requester or bound filer; a 👍 does nothing. Typed replies (approve file, approve) still do the same thing. Plain replies in a factory thread need no @Factory mention; only a new request starts with one. Outbound, the desk keeps one status reaction on the filer's original message so #mars-eng-intake shows where each request is: 👀 filed / Triaged → ⏳ planner running → 📝 Planned → 🛠️ Approved / In Progress → 🔍 In Review → ✅ Done, or ❓ when a person has to answer and ⚠️ when triage, the planner, or a launch stopped. A late webhook with an older Jira changelog id changes nothing. A Jira-filed ticket and a DM get no reactions. factory-worker starts a cloud agent and moves the ticket to In Progress. The agent opens the pull request; the worker comments Pull request: <url> once, then moves the ticket to In Review. If a check fails, the fixer drives a cloud run until CI passes. A person reviews and merges, never auto-merge, and the worker moves the ticket to Done. A ticket that needs information stays Triaged; a plain reply in the thread is added as Detail from Slack: and sent back to the planner.

Every Slack post covers only the current step: what just happened, or the one action the reader takes now (a Next: line only for that), never what comes later. The Filed post is one post: the ticket link with the KEY as link text and the triage it was filed with and who made it (Bug, low severity (triaged by Jev)); a desk-filed ticket gets no separate Triaged line for that verdict. The plan post is phone-sized: summary, approach, areas, tests, risk, size, then a "Full plan and worker brief" link to the Jira Plan: comment and one line asking for the decision on this plan: React ✅ to start the build or ❌ to stop, or reply approve / deny KEY. In a channel the desk does not watch, where a plain reply never reaches it, both asks are reactions only: React ✅ to file or ❌ to drop. and React ✅ to start the build or ❌ to stop. The filing writes Slack thread: <permalink> into the Jira description, and the planner's brief asks for Jira: then Slack: as the implement PR's first two description lines, under a KEY: <what> title.

This page follows the code on main (factory-desk/agent/lib/reaction-approval.ts, intake-triage.ts, review-update.ts). Older hop-by-hop notes are in verification.md. Deploy steps: factory-deployment.md. Jira rules: jira-automation.md.

Pull request quality gates mix Cursor product features (Bugbot, change-monitor) with factory BDK agents (factory-security-reviewer, factory-pr-autofixer) and Jira Automation rules. Each mechanism appears on a different GitHub surface — Checks tab, Reviews, or Conversation — so verifying a live end-to-end requires checking all three. This page tags each integration BDK, Cursor product, or Jira Automation so they are never conflated.

Check a run with node scripts/e2e-drive.mjs. Replay mode, the default, posts signed synthetic Jira events to each slug's route. Replay signs every route with the root .env.local JIRA_WEBHOOK_SECRET, so it works only while all four slugs hold that value. --live relies on the real TLSSN Automation rules and posts nothing.

The driver has no Slack step. It files the ticket and moves it to Approved through the Jira REST API, so the Slack filing, the ✅ reactions, and every desk post are not exercised, and it has no row for the worker's In Review and Done moves. With FACTORY_E2E_GITHUB_TOKEN unset, each GitHub write goes to one Cursor cloud agent, and the driver only reads GitHub to verify it. In that mode the factory: drive comment posts as cursor[bot], which Cursor's hosted GitHub ingress drops, so the drive row cannot pass and a person must type it; --cleanup cannot close pull requests in that mode.

It prints one row per step, marked pass, pass (prior run), fail, blocked, unverified, or skipped, and exits 1 on any fail. A blocked row names the precondition it lacks. A pass (prior run) row re-read state from before this run: a Jira hop the ticket had finished, reused pull requests, or a review, fix, or drive start that predates the run; nothing was sent or written for it. The drive and red-check rows pass only on a comment or push by a login in FACTORY_E2E_FIXER_LOGINS, which has no default until the fixer's GitHub identity is confirmed. A push's login is the actor of the push or pull_request workflow run GitHub started for the commit, never the commit's author, so a commit with no such run never counts. The review row passes only on a COMMENTED review of the pull request head by a login in FACTORY_E2E_REVIEWER_LOGINS (default cursor[bot]) whose body opens with ## Security review then **Verdict:** CLEAN or FINDINGS. At the timeout, activity only by a person, the driver, or a login outside the pin is fail (wrong actor); anything less certain leaves the row unverified. In cloud-agent mode the drive row does not exclude the driver's own login.

Five rules in the TLSSN project carry the status bus. Every rule sends a web request with method POST, header Content-Type: application/json, and the hidden header X-Factory-Webhook-Secret (its value is the slug's secret; never paste it into docs), with "Wait for response" unticked. Full setup: jira-automation.md.

Every free-text smart value uses .jsonEncodeSummary, description, reporter name, and comment body are encoded. An unescaped quote in a title made invalid JSON that the host dropped silently while Jira still logged "Successfully published web request". That broke planning for TLSSN-40/41.

Automations as code (cursor-agent + YAML)

The live factory runs as the six hosted Agent SDK (@cursor/july 0.2.18) deployments: the Jira rules above POST to the hosts' engine channel URLs, and GitHub events arrive through --cursor-events-repo. The same event wiring is also written as Cursor Automations config-as-code, one file per role at the repo root in .cursor/automations/factory-*.yaml, deployable with cursor-agent automations deploy. Each spec runs claude-opus-5-5 at low effort and its prompt points at the host's AGENTS.md in the checkout. There is no Jira trigger kind, so the Jira rules map to webhook: {}. Two out-of-the-box templates sit beside them, also enabled: false: find-vulnerabilities.yaml ("Find vulnerabilities" on marsbank PRs) and find-bugs.yaml ("Find critical bugs", not Bugbot). Bugbot, the managed Security Reviewer, and change monitor have no YAML form; turn them on in the dashboard (Bugbot rules live in .cursor/BUGBOT.md). Full guide: cursor-agent-automations.md.

The specs ship enabled: falseDeploying them next to the live hosts cannot double-handle an event. Enable one only when it replaces (or shadows, pointed elsewhere) the matching host. A disabled deploy still creates the record, so validate, get --yaml, and test work.
The automations verbs are gatedThey need the automations_config_as_code gate on the account. If cursor-agent automations --help prints only the main help, the gate is off. agent is the same binary.

Known limits and open follow-ups

  • Reactions count only on a post the desk recorded when it landed (the filing prompt, the plan post). A ✅ on anything else, or from anyone but the requester or filer, is ignored with no reply.
  • Two approve beats remain by design: ✅ on the filing prompt files the ticket, ✅ on the plan post builds it.
  • Marsbank implement pull requests are merged by a person. No agent merges and auto-merge is off; a bot or auto-merge merge never moves the ticket to Done.
  • A free-text Jira smart value without .jsonEncode breaks the rule body: TLSSN-40/41 were dropped silently while Jira logged "Successfully published web request". See Jira Automation rules.
  • The security reviewer still posts one review per pushed head, not one per verdict change.
  • Autofixer commits do not yet name the ticket key in their titles.
  • Review updates need factory-desk redeployed with --cursor-events-repo cursor-demo-lab/marsbank and FACTORY_REPOS set. Hosted delivery of pull_request_review is unverified, so a security review that lands after Bugbot and CI waits for the desk's 1, 3, and 6 minute re-reads or the next push. The autofix line is inferred from a bot push after red CI.
  • Tickets filed directly in Jira get no Slack thread link on the ticket or PR and no status reactions.
